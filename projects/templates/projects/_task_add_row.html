{% comment %} The one row that adds a task to a plan that already exists (#148). The sibling of _task_due.html and _task_dot.html, and it exists for the same reason: the markup that decides whether a write is offered lives in one template, so a second surface cannot re-derive the condition and get it wrong. Included by the dashboard's project section and by /mein-plan/'s list; the behaviour half is static/projects/js/task_add_row.js, so a third surface is an include plus one bindTaskAddRows() call. Two conditions, both inherited rather than invented here: viewing_demo_data — the demo example projects are in no session (#10 §5), so nothing in them can be written to. The endpoint answers 404 there, and a row that answers 404 on every submit is an affordance that is not there. sim_date — #217's rule that a Zeitreise moment is a rendering of a date, not a place to change things. Rescheduling is the documented exception because a new date visibly moves the task; an *added* task dated before the moment would be forced `done` by the simulated render the instant it appeared, which is exactly the invisible write #217 refused. project_id is passed in rather than read off a context variable: the dashboard includes this once per project section, and /mein-plan/ once for the one session plan. Which project a row belongs to is a statement about where it is included, the same way _task_due.html takes its due_display. Minimal input, name and date only (#148). No kontext select — that is the "full form page" the issue ruled out by another name, and #155's per-task durations will reopen this row's shape anyway. The accepted consequence is named in notion.py create_task: a task added here carries no kontext, so it is invisible to the cross-project batching hint the summary prompt derives from one (#145). The date starts on today and is asked for the way every other date in the app is asked for (#279). Three things about it that look like omissions and are not: Today is safe here precisely because of the two conditions above. A Zeitreise moment renders nothing of this row, so "today" can never be read against a simulated date — #217's rule is inherited, not restated. No stage class. .task-due carries `today`, `urgent` or `overdue` on a task row, and urgency is a property of a task that exists; there is none yet. Painting one would also mean re-deriving _classify_due_urgency in JavaScript on every pick, which #198 settled the other way. No data-task-id, deliberately. That attribute is the contract bindTaskDatePickers() binds on (task_date_picker.js), and a row with no task would hand it an undefined id to reschedule. The add row calls the module's other entry point itself instead, so what it shares is the asking and not the contract. date_role is required rather than defaulted, and it is the including surface's rather than this partial's. The defect #279 was about was a row asking for the same kind of value in a spelling nothing else on the page uses — so pinning one role here would have carried that defect onto /mein-plan/, whose list writes the month out (the "long" role) where the dashboard's rows abbreviate it (the "row" one). Same reasoning as the due_display _task_due.html takes in: which form a date is spelled in is a statement about the surface, settled per surface by #238. An include that forgets it fails loudly in date_names rather than rendering a shape at random. The two name tables travel as data attributes because the label has to be recomposed in the client after a pick: every other surface gets its new label from the write's own response, and this row's pick writes nothing. date_format.py stays the one source of the names (planner_tags.date_names), which hands over the tables that role spells with, and of the shape they go into (planner_tags.date_pattern), which is whatever DATE_STYLE resolves the role to (#192).
